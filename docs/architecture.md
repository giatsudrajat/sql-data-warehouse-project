# Architecture and design decisions

## Layers and refresh behavior

| Layer | Storage | Refresh | Purpose |
| --- | --- | --- | --- |
| Bronze | Six physical tables | Truncate and bulk import each source file | Typed staging with source-shaped columns |
| Silver | Six physical tables | Truncate and insert transformed Bronze rows | Cleaned and standardized data |
| Gold | Three core views and two report views | Calculated when queried | Integration, dimensions, sales facts, and reporting |

Bronze preserves source-shaped values within declared SQL types; it is not an immutable raw-file archive. Silver includes `dwh_create_date` as a load timestamp. Gold does not persist a second copy of the data.

The procedures print timing/error information to the client. They rethrow errors but do not wrap the full multi-table refresh in a transaction. There is no scheduler, retry controller, audit table, or incremental watermark.

## Source-to-model mapping

| Input | Silver use | Gold destination |
| --- | --- | --- |
| CRM customer information | Deduplicated CRM identity and attributes | `dim_customers` |
| ERP customer information | Birth date and fallback gender | `dim_customers` |
| ERP location information | Customer country | `dim_customers` |
| CRM product information | Product identifiers, costs, and validity dates | `dim_products` |
| ERP product categories | Category, subcategory, maintenance | `dim_products` |
| CRM sales details | Dates, quantities, sales, and prices | `fact_sales` |

## Transformation rules

| Subject | Implemented rule |
| --- | --- |
| CRM customers | Exclude NULL customer IDs; keep one row per ID ordered by the latest creation date; trim names and map gender/marital status |
| CRM products | Extract category and product keys; replace missing cost with zero; map product-line codes; derive end dates with `LEAD` |
| Sales dates | Convert integer dates with `TRY_CONVERT`; set invalid or inconsistent order/shipping dates to NULL |
| Sales measures | Derive missing/nonpositive prices when possible; recalculate missing, nonpositive, or inconsistent sales; preserve the current integer storage contract |
| ERP customers | Remove a leading `NAS`; set future birth dates to NULL; normalize gender |
| ERP locations | Remove hyphens from customer IDs; standardize selected country codes and missing values |
| ERP categories | Normalize maintenance labels |
| Customer gender | Prefer CRM unless missing or `n/a`; fall back to ERP |
| Current products | Include only Silver product rows with `prd_end_dt IS NULL` |

Equal customer creation dates have no explicit tie-breaker. Missing product cost becomes zero, so downstream reports cannot distinguish that missing value from a genuine zero cost. These are known modeling limitations.

## Grain and joins

`gold.dim_customers` is intended to contain one row per CRM customer ID. ERP inputs must not multiply that row through duplicate customer IDs.

`gold.dim_products` is intended to contain one current row per product number. Category IDs must not multiply rows through duplicate category records.

`gold.fact_sales` retains each Silver sales-detail row, subject to the joins preserving that grain. An order can contain multiple rows; `order_number` alone is not a fact-row identifier. No order-line identifier or enforced uniqueness constraint is present.

All core integration joins are LEFT JOINs. Unmatched sales remain visible, but their generated customer/product keys are NULL. Reports group those records into unknown-key buckets; the original missing source identities are not exposed in the fact view.

## Key strategy and history

Customer and product keys are `BIGINT` values generated by `ROW_NUMBER()` in views. They are query-time identifiers, not persisted surrogate-key allocations. Source changes can change the numbering; ties can also affect determinism. Do not cache these keys in external systems as permanent identifiers.

Silver product rows retain derived validity intervals, but Gold selects current product versions. Historical sales are joined to the current product by product number, not by an effective-date range. The implementation is not a historical SCD Type 2 fact-to-dimension model.

See [Data quality](data_quality.md) for business-key checks and Silver-to-Gold row-count/revenue reconciliation.

## Reporting decisions

- Customer and product reports include sales with non-NULL order dates.
- Lifespan is the inclusive span from the first to last dated sale; intervening months without sales are included.
- Recency and customer age use the SQL Server clock via `GETDATE()`, so they change over time even without a reload.
- Customer segmentation is defined in `gold.report_customer`; the segmentation query reads that view to avoid duplicate rules.
- The SQL object name `gold.report_customer` remains singular for compatibility.
